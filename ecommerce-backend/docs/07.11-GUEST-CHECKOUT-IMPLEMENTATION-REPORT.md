# Phase 07.11 — Guest Checkout Implementation Report

## 1. Executive Summary

Phase 07.11 delivers the **Guest Checkout Subsystem** for the Nexora Commerce Platform, enabling frictionless purchasing without requiring account creation while maintaining strong cryptographic security guarantees, timing-attack resistance, zero raw-token persistence, strict anti-IDOR authorization boundaries, race-safe inventory reservations, and idempotent response replay contracts.

---

## 2. Core Architecture & Security Invariants

### 2.1 Cryptographic Token Security
- **Entropy & Generation**: Tokens are generated via `crypto.randomBytes(32)`, providing 256 bits of high entropy, formatted as 64-character hexadecimal strings.
- **One-Way Storage at Rest**: Only the SHA-256 hash (`crypto.createHash('sha256').update(rawToken).digest('hex')`) is persisted in `orders.guest_token_hash`.
- **Zero Raw Token Persistence**: Raw guest tokens are never written to disk, database tables (`orders`, `idempotency_records`), session stores, log files, or error messages.
- **Timing-Attack Resistance**: Verification uses `crypto.timingSafeEqual` with strict buffer length checks to prevent timing side-channel attacks.
- **Deep Redaction**: Logger sensitive key patterns include `guest_token`, `guesttoken`, `x-guest-token`, `guest_token_hash`, and `guesttokenhash`.

### 2.2 Canonical Headers & Unified Entry Points
- **Single Canonical Header**: `X-Guest-Token` is the sole canonical header accepted for guest authorization. No deprecated aliases (`X-Guest-Order-Token`) are supported.
- **Unified Checkout Initiation**: `POST /api/checkout/initiate` serves as the single unified checkout route for both authenticated customer cart conversions and direct guest checkouts.
- **No Secondary CSRF**: Reuses the hardened Phase 07.3 Double-Submit CSRF protection (`verifyCsrf`).

### 2.3 Guest Payment Authorization Chain
1. `X-Guest-Token` header is supplied with payment requests (`POST /api/payments/create-order`, `/retry`, `/verify`).
2. Order is loaded and authorized against `orders.guest_token_hash` in constant time.
3. Server verifies that the `PaymentAttempt` strictly belongs to that authorized guest order.
4. Server-authoritative amounts and inventory transitions execute under standard transaction isolation.
5. Missing, invalid, expired (>30 days), or cross-tenant guest tokens return sanitized `404 ORDER_NOT_FOUND` (zero IDOR information leakage).

### 2.4 Idempotency & Zero-Storage Replay Contract
- The initial checkout response returns the raw `guestToken` exactly once.
- Idempotency records store sanitized snapshots with `guestToken: null` in the database.
- Subsequent replays of the same `Idempotency-Key` return HTTP 201 with `X-Idempotent-Replay: true` and `guestToken: null`, strictly preventing raw token persistence or regeneration.
