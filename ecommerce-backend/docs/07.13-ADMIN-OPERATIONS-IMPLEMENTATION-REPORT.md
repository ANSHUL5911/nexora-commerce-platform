## 2. Surgical Scope Corrections & Domain Boundaries

### 2.1 Removed Proposed Operations & Rationale
- **Removed Direct Inventory Restock (`POST /api/admin/inventory/restock` & generic restock service):** Phase 07.12 already established the authoritative physical restocking model (`POST /api/admin/orders/:orderId/restock` linked to an explicit `StockRestockLog` referencing a refunded order). Direct warehouse stock-increment operations were eliminated to prevent introducing a divergent, un-audited, or orderless inventory mutation path. `StockRestockLog.order_id` remains strictly non-nullable.
- **Removed `stock_quantity` and `reserved_quantity` from Product PATCH (`PATCH /api/admin/products/:id`):** Inventory is an operational domain state managed by Phase 07.6/07.12, not a mutable product catalog field. Product PATCH endpoints strictly permit only catalog attributes (`name`, `description`, `price_paise`, `category`, `image_url`). Any attempt to modify stock counts via product update endpoints is rejected with validation errors.
- **Removed `trackingNumber`:** Verified against Migration 006, `Order` model, and database schema. Because `orders` table does not have a `tracking_number` column and speculative migrations are strictly forbidden, `trackingNumber` was removed from request schemas, DTOs, services, controllers, and tests.
- **Removed `is_deleted` from Product PATCH:** Product soft-deletion is strictly handled via `DELETE /api/admin/products/:id`, preventing arbitrary persistence terminology leakage into generic update payloads.

### 2.2 Product Initial Stock Handling
- When creating a product via `POST /api/admin/products`, `stock_quantity` initializes the inventory count ($\ge 0$), and `reserved_quantity` is strictly initialized to `0`. `available_quantity` is computed as `stock_quantity - reserved_quantity`.
- This is purely catalog initialization, not a restock event, so no `StockRestockLog` is created. The creation event is atomically logged in `AuditLog`.

### 2.3 Order Cancellation & Reservation Release
- When an order in `PENDING_PAYMENT` state is cancelled via `PATCH /api/admin/orders/:orderId/status`, the admin order service delegates reservation release to Phase 07.6 (`inventoryService.releaseReservation`).
- This ensures `reserved_quantity` is decremented safely within the transaction, the `InventoryReservation` status becomes `RELEASED`, and order status transitions to `CANCELLED`. If reservation release fails, the entire transaction rolls back.

### 2.4 Refund & Restock Delegation
- Administrative refund (`POST /api/admin/orders/:orderId/refund`) and administrative restock (`POST /api/admin/orders/:orderId/restock`) remain 100% delegated to the sealed Phase 07.12 services.
- Phase 07.13 did not duplicate Razorpay refund logic, idempotency handling, payment attempt transitions, or restock item calculations.

### 2.5 Atomic Audit Logging
- Every administrative state mutation (product create/update/soft-delete, order status change) inserts an `AuditLog` row within the exact same PostgreSQL transaction as the domain mutation.
- Audit metadata is strictly sanitized via recursive allowlists, preventing any leakage of passwords, tokens, API keys, or payment details.

## 3. Endpoints Implemented

### 3.1 Product Operations
- `GET /api/admin/products` — Paginated admin catalog listing with status filtering (`status=active|deleted|all`), search, and sorting.
- `GET /api/admin/products/:id` — Detailed product view including internal stock and reservation counts.
- `POST /api/admin/products` — Create product with catalog fields and initial stock quantity; logs `ADMIN_PRODUCT_CREATE`.
- `PATCH /api/admin/products/:id` — Update catalog attributes only (`name`, `description`, `price_paise`, `category`, `image_url`); logs `ADMIN_PRODUCT_UPDATE`.
- `DELETE /api/admin/products/:id` — Soft-delete product (`is_deleted = true`); logs `ADMIN_PRODUCT_DELETE`. Historical `OrderItem` price and name snapshots remain untouched.

### 3.2 Inventory Operations
- `GET /api/admin/inventory` — Paginated read-only inventory overview with `lowStockThreshold` filter, calculating `available_quantity = stock_quantity - reserved_quantity`.

### 3.3 Order Operations
- `GET /api/admin/orders` — Paginated admin orders list with filtering by `status`, `userId`, `guestEmail`, and deterministic sorting.
- `GET /api/admin/orders/:orderId` — Comprehensive order details with associated items, payments, and restock logs.
- `PATCH /api/admin/orders/:orderId/status` — State machine transition enforcing `ALLOWED_STATUS_TRANSITIONS`. On `PENDING_PAYMENT -> CANCELLED`, releases inventory reservations; logs `ADMIN_ORDER_STATUS_CHANGE`.

### 3.4 Sealed Phase 07.12 Operations (Delegated)
- `POST /api/admin/orders/:orderId/refund` — Gateway refund execution (Phase 07.12).
- `POST /api/admin/orders/:orderId/restock` — Physical inventory restock for refunded orders (Phase 07.12).

### 3.5 Audit Log Operations
- `GET /api/admin/audit-logs` — Admin-only paginated audit trail query with bounded pagination, action filtering, resource filtering, actor filtering, and date range filtering.
