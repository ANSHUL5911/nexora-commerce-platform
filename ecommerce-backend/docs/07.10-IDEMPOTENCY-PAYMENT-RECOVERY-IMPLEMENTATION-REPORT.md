## 1. Executive Summary

Phase 07.10 implements production-grade, request-level idempotency and transactional payment recovery across the Nexora Commerce Platform. The subsystem guarantees strict at-most-once semantics across distributed client retries, server interruptions/crashes, and external payment gateway ambiguities.

### Core Guarantees Delivered
1. **At-Most-Once State Mutations**: Zero duplicate Orders, zero duplicate PaymentAttempts, zero duplicate inventory deductions, and zero duplicate payment settlements under arbitrary concurrency, repeated requests, network dropouts, and process terminations.
2. **Deterministic Dual-Path Concurrency Control**:
   - Genuinely active in-flight requests receive standard HTTP `409 IN_PROGRESS` (`IDEMPOTENCY_IN_PROGRESS`) responses.
   - Finished operations deterministically replay identical cached responses (`status_code`, `headers`, and canonical `response_body`) without re-executing business logic.
   - Failed recoverable operations cleanly transition to `FAILED_RETRYABLE` and permit atomic re-claiming.
3. **Transactional Atomic Commitments**: Business state transitions and idempotency record status updates execute within shared PostgreSQL database transactions (`FOR UPDATE` row-level locks).
4. **Crash-Resilient Recovery**: Stalled `IN_PROGRESS` records past their expiration threshold (`expires_at`) are automatically evaluated against persisted entity references (`PaymentAttempt` / `Order`) to either finalize cached responses or release the lock for safe re-execution.
5. **Ambiguous Gateway Timeout Handling**: Gateway timeouts during order creation are cleanly recorded with `FAILED_RETRYABLE` and `GATEWAY_ERROR` without leaking unverified states or making HTTP calls inside database transactions.

## 3. Implementation Details

### 3.1. Canonical Fingerprint & Request Hashing
Idempotency record lookups are bound strictly to:
- `user_id` (authenticated user UUID)
- `idempotency_key` (client-provided header, sanitized UUID/opaque string up to 255 chars)
- `request_path` (`/api/orders`, `/api/payments/create-order`, `/api/payments/retry`, `/api/payments/verify`)
- `request_hash` (Canonical SHA-256 hash computed over `userId + method + path + sorted(body)`)

If a client submits an identical `Idempotency-Key` with a modified payload or different endpoint, the middleware rejects the request with HTTP `422 UNPROCESSABLE ENTITY` (`IDEMPOTENCY_KEY_REUSE_MISMATCH`).

### 3.2. Lifecycle State Machine
```
              [ Client Request ]
                      │
                      ▼
         [ Pre-claim Idempotency Record ]
                      │
        ┌─────────────┴─────────────┐
        ▼                           ▼
[ Existing Record ]          [ New Record ]
        │                           │
  ┌─────┼─────────────┐             ▼
  │     │             │     Status: IN_PROGRESS
  │     │             │     (Set expires_at)
  ▼     ▼             ▼             │
[COMPLETED] [IN_PROGRESS] [FAILED]  │
  │     │             │     │       ▼
  │     │             │     └──> [ Re-claim / Safe Retry ]
  │     ▼             │             │
  │  [Active]         ▼             ▼
  │     │      [Expired/Stalled] ──> [ Inspect Persisted DB State ]
  │     ▼             │                     │
  │  HTTP 409         ├─────────────────────┼─────────────────────┐
  │  IN_PROGRESS      ▼                     ▼                     ▼
  │              [Entity Found]      [Entity Found]        [No Mutation]
  │              (Order/Paid)        (Failed/Initiated)          │
  │                   │                     │                    ▼
  │                   ▼                     ▼           Mark FAILED_RETRYABLE
  │              Mark COMPLETED      Mark FAILED_RETRYABLE  & Execute Operation
  │                   │                     │
  ▼                   ▼                     ▼
[ Replay Cached 200/201 Response ]   [ Execute Fresh Attempt ]
```

### 3.3. Transactional Consistency & Crash Recovery
- **No Res.json-Only Completion**: Idempotency records are completed directly inside the underlying business transactions using the active Sequelize transaction handle. If the transaction rolls back, the idempotency record rolls back or records `FAILED_RETRYABLE`.
- **Database Row Lock Protection**: Recovery evaluations execute under `SELECT ... FOR UPDATE` row locks inside PostgreSQL. Concurrent requests for an expired record are serialized: exactly one evaluates recovery and executes, while subsequent requests replay the outcome or receive `409 IN_PROGRESS`.
- **Gateway Timeout Ambiguity**: When Razorpay `createOrder()` suffers a network timeout before obtaining a remote ID, the local `PaymentAttempt` is marked `GATEWAY_ERROR` and the idempotency record is marked `FAILED_RETRYABLE`. The unknown remote gateway order is isolated as an external reconciliation concern without corrupting Nexora inventory or balances.
