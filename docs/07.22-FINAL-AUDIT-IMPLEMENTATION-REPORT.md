## 5. Backend Audit

### Authentication
- **Registration**: Enforces strong password criteria via Zod; hashes passwords with native `bcrypt` (`^6.0.0`, resolved to `6.0.0` in `package-lock.json`) at cost 12 with native C++ bindings in `src/modules/auth/password.js` (note: while earlier Phase 07.3 design documents initially referenced `bcryptjs`, the active repository implementation uses native `bcrypt` exclusively; `bcryptjs` is absent from `package.json` and `package-lock.json`); generates 256-bit random session identifiers upon registration; sets secure cookie flags.
- **Login & Anti-Enumeration**: Validates credentials using timing-consistent dummy password hashing on unknown accounts (`bcrypt.compare(password, DUMMY_HASH)`) to eliminate timing side-channels; rotates session ID on authentication to prevent session fixation attacks.
- **Session Expiration**: Enforces 7-day rolling expiry (`SESSION_MAX_AGE_MS = 604800000`); stale or expired sessions in database are purged and return 401.
- **Logout**: Explicitly deletes session row from database; clears `__Host-nexora_sid` cookie with explicit matching security flags (`Secure=true`, `Path=/`, `HttpOnly=true`).
- **Audit Verification**: `tests/auth/auth.api.test.js` (13 tests passed).

### Authorization & IDOR
- **Role-Based Access Control**: Strict segregation between `customer` and `admin` roles via `requireAuth` and `requireAdmin` middlewares; unauthorized customer access to admin routes returns 403 `FORBIDDEN`.
- **Cart Isolation**: Cart operations strictly bind to `req.user.id`; customers cannot access or mutate another customer's cart.
- **Order Scoping**: Orders retrieved via `GET /api/orders/:orderId` enforce ownership validation against authenticated `userId` or guest token hash; cross-customer lookups return sanitized 404 `ORDER_NOT_FOUND`.
- **Payment Scoping**: Payment initiation and retry routes verify that the target order belongs to the requester before creating gateway orders.
- **Audit Verification**: `tests/admin/authorization.test.js` (18 tests passed), `tests/cart/cart.api.test.js` (24 tests passed).

### Catalog
- **Read Model**: Public `GET /api/products` supports deterministic ordering (`created_at DESC, id DESC`), pagination (default 10, maximum 50), category filtering, and text search.
- **Availability Projection**: Returns `available_quantity` computed server-side (`stock_quantity - reserved_quantity`); clients never derive stock arithmetic.
- **Soft Deletion**: Soft-deleted products (`is_deleted = true`) are filtered from public listings but preserved for historical order relationships.
- **Query Efficiency**: Catalog queries execute in 2 queries (count + rows); zero N+1 queries.
- **Audit Verification**: `tests/catalog/catalog.api.test.js` (16 tests passed).

### Cart
- **Operations**: `POST /api/cart/items`, `PATCH /api/cart/items/:id`, `DELETE /api/cart/items/:id`, and `DELETE /api/cart`.
- **Validation**: Enforces quantity bounds (1 <= quantity <= 10); validates current product availability; updates cart timestamp; performs zero inventory reservations or mutations during cart operations.
- **Audit Verification**: `tests/cart/cart.api.test.js` (24 tests passed).

### Inventory
- **Atomic Reservations**: Created during checkout via `inventoryService.reserveInventory` with a 15-minute expiration determined authoritatively by PostgreSQL (`NOW() + INTERVAL '15 minutes'`).
- **Multi-Product Row Locking**: Products are locked using `SELECT ... FOR UPDATE` ordered by ascending UUID (`id ASC`) to eliminate database deadlocks during multi-item checkouts.
- **Lifecycle Transitions**: State machine transitions (`ACTIVE` → `CONVERTED`, `ACTIVE` → `RELEASED`, `ACTIVE` → `EXPIRED`) execute atomically within transaction boundaries.
- **Expiration Mechanism**: Expired reservations are evaluated against PostgreSQL `CURRENT_TIMESTAMP`; releasing expired reservations is handled via the internal maintenance method `inventoryService.releaseExpiredReservations` using explicit row locks, without depending on external background worker infrastructure or Redis schedulers.
- **Audit Verification**: `tests/inventory/inventory.concurrency.test.js` (7 tests passed).

### Orders
- **Checkout Initiation**: `POST /api/checkout/initiate` orchestrates Order creation, OrderItem snapshotting (price, name, SKU), inventory reservation, and cart clearing within a single ACID transaction.
- **External Call Separation**: Gateway calls (Razorpay order creation) are strictly performed **outside** the database transaction boundary.
- **State Machine**: Order status follows a controlled, explicitly permitted state-transition model: `PENDING_PAYMENT` → `PAID` → `PROCESSING` → `SHIPPED` → `DELIVERED`, with terminal and cancellation branches `CANCELLED`, `EXPIRED`, and `REFUNDED`.
- **Schema & DTO Field Mapping**: The PostgreSQL `orders` table physically persists `total_cost_paise` (BIGINT) and `shipping_fee_paise` (BIGINT). The Sequelize `Order` model provides a virtual/derived getter for `subtotal_paise` (`total_cost_paise - shipping_fee_paise`); `total_amount_paise` is not a column. The DTO serialization layer (`order.dto.js`) exposes `subtotalPaise`, `shippingFeePaise`, `totalPaise` (canonical frontend DTO), and `totalCostPaise` (backward-compatible alias).
- **Audit Verification**: `tests/orders/order.service.test.js` (11 tests passed), `tests/orders/order.concurrency.test.js` (2 tests passed).

### Payments
- **Gateway Integration**: Razorpay TEST mode; credentials (`RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`) are strictly backend-only.
- **PaymentAttempt Lifecycle**: Tracks gateway attempts per order (`INITIATED` → `SUCCESS` / `FAILED`). In Phase 07.12, the status `REFUNDED` was incorporated in the database schema CHECK constraint and model validation (`status IN ('INITIATED', 'SUCCESS', 'FAILED', 'REFUNDED')`) to record settled attempts that have undergone an administrative full capital refund.
- **Retry Semantics**: If a payment attempt fails, `POST /api/payments/retry` creates Attempt #2 and generates a **new Razorpay Order ID** linked to the **same ecommerce Order**. A new ecommerce Order is never created for a retry.
- **Payment Verification**: `POST /api/payments/verify` performs HMAC-SHA256 signature verification, server-side Razorpay order fetch reconciliation, and delegates to the shared settlement service.
- **Audit Verification**: `tests/payments/payment.service.test.js` (14 tests passed), `tests/payments/payment.concurrency.test.js` (2 tests passed).

### Webhooks
- **Signature Validation**: `POST /api/webhooks/razorpay` captures the raw request body buffer before JSON parsing and validates `x-razorpay-signature` using HMAC-SHA256 with `crypto.timingSafeEqual`.
- **Event Deduplication**: Every event is recorded in `payment_events` with a UNIQUE constraint on `event_id`. Duplicate deliveries are safely flagged as `IGNORED_DUPLICATE` and return 200 OK without re-executing business effects.
- **Late Capture Handling**: If a `payment.captured` event arrives after an order has expired, the payment attempt is recorded as `SUCCESS`, the order remains `EXPIRED`, and the event is routed to `REQUIRES_REFUND` without corrupting inventory.
- **Audit Verification**: `tests/payments/webhook.api.test.js` (7 tests passed), `tests/payments/webhook.signature.test.js` (7 tests passed).

### Idempotency
- **Mechanism**: State-changing endpoints accept `Idempotency-Key` headers; records are keyed by `UNIQUE(idempotency_key, request_path)`.
- **State Machine**: States progress through `IN_PROGRESS` → `COMPLETED` or `FAILED_RETRYABLE`. Concurrent requests on an active key conflict safely with 409; exact replays return cached responses with `X-Idempotent-Replay: true`.
- **Crash Recovery**: If an operation is interrupted during payment creation, subsequent requests safely reuse existing gateway orders if persisted.
- **Audit Verification**: `tests/idempotency/idempotency.concurrency.test.js` (4 tests passed), `tests/idempotency/idempotency.repository.test.js` (8 tests passed).

### Guest Checkout
- **Token Generation**: Generates 256-bit CSPRNG token (`crypto.randomBytes(32).toString('hex')`) during `POST /api/checkout/initiate`; returns raw token once in response payload.
- **Storage**: Raw token is hashed with SHA-256 and stored in `orders.guest_token_hash`; raw token is never persisted in database, never logged, and never placed in URLs.
- **Verification**: Guest order retrieval (`GET /api/orders/:orderId` with `X-Guest-Token`) hashes the provided header and performs length validation followed by `crypto.timingSafeEqual`.
- **Audit Verification**: `tests/orders/guest.token.test.js` (9 tests passed), `tests/orders/guest.concurrency.test.js` (2 tests passed).

### Refunds & Restocking
- **Refund Service**: `POST /api/admin/orders/:id/refund` verifies settled status, locks records, transitions to `REFUNDED`, commits, and calls the Razorpay Refund API. **Critically, refund operations do NOT modify product inventory.**
- **Restock Service**: `POST /api/admin/orders/:id/restock` is an independent administrative operation executed after physical inspection. It locks products in ascending UUID order, validates remaining eligible quantities against historical logs, increments stock, and writes immutable `StockRestockLog` and `AuditLog` entries.
- **Audit Verification**: `tests/admin/refund_restock.e2e.test.js` (2 tests passed), `tests/admin/admin.operations.e2e.test.js` (5 tests passed).

### Observability
- **Structured JSON**: All application logs use standard JSON format containing `timestamp`, `level`, `service`, `environment`, `event`, `requestId`, `method`, `path`, `statusCode`, `durationMs`, and `actorType`.
- **Sensitive Redaction**: `src/utils/logger.js` enforces a comprehensive blocklist of 63 sensitive keys (passwords, tokens, cookies, keys, card numbers, CVVs) and regex pattern sanitizers.
- **Decoupled Audit Logging**: Operational `AuditLog` records business actions (product updates, order status changes, refunds, restocks) independently of operational log streams.
- **Audit Verification**: `tests/observability/observability.test.js` (31 tests passed).

## 7. Security Audit & Threat Model

### Threat Model Matrix

| Threat Category | Attack Vector | Nexora Mitigation | Status |
| :--- | :--- | :--- | :--- |
| **Credential Stuffing / Brute Force** | High-frequency login attempts | IP-based authentication rate limiter (5 req / 1 min); native bcrypt cost 12; dummy hash path prevents timing enumeration. | 🛡️ MITIGATED |
| **Session Fixation** | Forcing pre-existing session ID | Server generates a new 256-bit random session identifier upon login and invalidates previous session. | 🛡️ MITIGATED |
| **Session Hijacking / Theft** | XSS stealing cookies | Session cookie configured with `HttpOnly=true`, `Secure=true` in production, `SameSite=Lax`, and `Path=/`. JavaScript cannot read the session cookie. | 🛡️ MITIGATED |
| **Cross-Site Request Forgery (CSRF)** | Malicious third-party state mutation | Double-submit CSRF cookie (`nexora_csrf`) + header (`x-csrf-token`) verified via `crypto.timingSafeEqual` on all state-changing requests. | 🛡️ MITIGATED |
| **Cross-Site Scripting (XSS)** | Injection via product/catalog/user-controlled application data | React automatic HTML entity escaping; Helmet Content Security Policy; strict input validation with Zod; zero `dangerouslySetInnerHTML`. | 🛡️ MITIGATED |
| **Insecure Direct Object Reference (IDOR)** | Tampering with orderId/userId in requests | Every route validates authenticated user ownership or guest token hash; cross-customer access returns sanitized 404. | 🛡️ MITIGATED |
| **Payment Amount Tampering** | Client submitting modified price | Prices and amounts are computed authoritatively on the backend from database catalog snapshots in integer paise; client-supplied prices are strictly rejected. | 🛡️ MITIGATED |
| **Webhook Forgery** | Spoofed payment capture events | Raw-body HMAC-SHA256 signature verification against `RAZORPAY_WEBHOOK_SECRET` using timing-safe comparison; duplicate event ID protection. | 🛡️ MITIGATED |
| **Inventory Overselling** | Concurrent checkouts on scarce stock | PostgreSQL row-level locks (`SELECT ... FOR UPDATE`); `chk_products_reserved_lte_stock` database constraint; ACID transaction rollback. | 🛡️ MITIGATED |
| **Guest Token Enumeration** | Brute-forcing guest tracking URLs | Cryptographically secure 256-bit random tokens; SHA-256 hash comparison with timingSafeEqual; 15 req / 15 min rate limiter. | 🛡️ MITIGATED |
| **IP Spoofing / Rate-Limit Bypass** | Fake `X-Forwarded-For` headers | Strict `TRUST_PROXY` validation in Express; rate limiters consume validated `req.ip` rather than raw client headers. | 🛡️ MITIGATED |
| **Sensitive Log Leakage** | Tokens/passwords appearing in stdout | Automated redaction in `logger.js` scrubbing 63 sensitive keys, credit cards, bearer tokens, and connection strings. | 🛡️ MITIGATED |

## 8. Database & Relational Integrity Audit

### Schema Inspection
- Database: PostgreSQL 16.15 (`nexora_test`, `nexora_dev`)
- Migration Engine: Umzug 3.8.3 with `SequelizeMeta` table authority.
- `sequelize.sync()` is strictly prohibited across all environments.

### Complete Database Table Inventory (14 Domain Tables + 1 Metadata Table)
The relational database contains exactly 14 domain / business tables plus the migration metadata table:
1. **`addresses`**: Stores customer shipping addresses; foreign key to `users`.
2. **`audit_logs`**: Immutable operational audit trail; records actor, action, resource, IP, and timestamp.
3. **`cart_items`**: Line items within carts; composite uniqueness on `(cart_id, product_id)`; quantity check `(1 <= quantity <= 10)`.
4. **`carts`**: Customer shopping carts; unique foreign key on `user_id`.
5. **`idempotency_records`**: Request deduplication journal; `UNIQUE(idempotency_key, request_path)`; tracks request hash and cached responses.
6. **`inventory_reservations`**: 15-minute checkout reservations; foreign keys to `products` and `orders`; status check constraint (`ACTIVE`, `CONVERTED`, `RELEASED`, `EXPIRED`).
7. **`order_items`**: Immutable historical line item snapshots (`price_paise_snapshot`, `product_name_snapshot`, `sku_snapshot`).
8. **`orders`**: Ecommerce orders; unique index on `id`; status check constraint (`PENDING_PAYMENT`, `PAID`, `PROCESSING`, `SHIPPED`, `DELIVERED`, `CANCELLED`, `EXPIRED`, `REFUNDED`); physical monetary columns stored in integer paise: `total_cost_paise` (BIGINT, not null) and `shipping_fee_paise` (BIGINT, default 0). The Sequelize `Order` model exposes `subtotal_paise` as a virtual/derived getter (`total_cost_paise - shipping_fee_paise`); `total_amount_paise` is not a physical column. Canonical DTOs expose `subtotalPaise`, `shippingFeePaise`, `totalPaise` (canonical frontend DTO), and `totalCostPaise` (backward-compatible alias).
9. **`payment_attempts`**: Tracks gateway attempts per order; status check constraint (`status IN ('INITIATED', 'SUCCESS', 'FAILED', 'REFUNDED')`); unique index on `razorpay_order_id`.
10. **`payment_events`**: Webhook event journal; `UNIQUE(event_id)` prevents duplicate processing.
11. **`products`**: Catalog items; primary key UUID; integer `price_paise`, `stock_quantity`, `reserved_quantity`; boolean `is_deleted`.
    - **Constraint**: `chk_products_reserved_lte_stock` enforces `reserved_quantity <= stock_quantity` and non-negativity.
12. **`sessions`**: Server sessions; primary key `sid` (256-bit hex); foreign key `user_id` references `users(id)` ON DELETE CASCADE; indexed `expires_at`.
13. **`stock_restock_logs`**: Immutable log of physical restocks; records `quantity_restocked`, `initiated_by`, `reason`.
14. **`users`**: System accounts; primary key UUID; unique index on `email`; role check constraint (`CUSTOMER`, `ADMIN`).
15. **`SequelizeMeta`**: Umzug migration tracking metadata table recording executed migration filenames.

### Migration Lifecycle & Rollback Verification

- Verified clean rollback of all 14 domain tables (+ `SequelizeMeta`) and full re-application with zero schema drift.

## 9. Concurrency & Race Condition Audit

All concurrency tests were executed directly against real PostgreSQL with active transaction boundaries:

### Scenario 1: Scarce Inventory Contention (Stock = 1, 10 Concurrent Requests)
- **Condition**: Product created with `stock_quantity = 1`, `reserved_quantity = 0`.
- **Action**: 10 simultaneous checkout requests fired across 10 distinct customer accounts.
- **Expected Outcome**: Exactly 1 request succeeds (HTTP 201); exactly 9 requests receive HTTP 400/409 `INSUFFICIENT_STOCK`. Database invariants hold (`stock = 1`, `reserved = 1`, `available = 0`). Zero overselling.
- **Actual Result**: **PASSED**. Exactly 1 succeeded, 9 rejected. Zero negative available stock.

### Scenario 2: Webhook Duplicate Delivery Race (10 Concurrent Identical Events)
- **Condition**: Single order in `PENDING_PAYMENT` with `ACTIVE` reservation.
- **Action**: 10 simultaneous `POST /api/webhooks/razorpay` requests with identical `event_id` and payload.
- **Expected Outcome**: All 10 requests return HTTP 200 OK. Exactly 1 `PaymentEvent` row persisted. Exactly 1 stock deduction occurred. Terminal state `PAID`.
- **Actual Result**: **PASSED**. Exactly 1 event processed, 1 stock deduction, order settled to `PAID`.

### Scenario 3: Verify vs. Webhook Race (Settlement Disambiguation)
- **Condition**: Client calls `POST /api/payments/verify` while Razorpay webhook captures simultaneously.
- **Action**: Both requests execute concurrently.
- **Expected Outcome**: First claimant executes settlement and stock conversion; second claimant detects settled state and returns idempotently. Order status is `PAID`, stock deducted once.
- **Actual Result**: **PASSED** (executed in 817 ms). Zero duplicate deductions.

### Scenario 4: Guest Checkout Idempotency Race (10 Concurrent Requests, Same Key)
- **Condition**: 10 identical guest checkout payloads fired concurrently with the same `Idempotency-Key`.
- **Expected Outcome**: Exactly 1 ecommerce Order created; exactly 1 reservation; exactly 0 duplicate gateway orders; zero guest token leaks.
- **Actual Result**: **PASSED** (executed in 600 ms). Exactly 1 order created.

## 11. Inventory Invariant & Availability Audit

### Invariant Equation
$$\text{available\_quantity} = \text{stock\_quantity} - \text{reserved\_quantity}$$

### Verification Results
1. **Client Isolation**: The frontend catalog adapter displays `available_quantity` provided by the backend. The frontend never computes stock subtractions.
2. **Database Constraint**: `chk_products_reserved_lte_stock` prevents any transaction from driving `reserved_quantity > stock_quantity` or causing negative stock.
3. **Deadlock Prevention**: When an order contains multiple products, they are queried and locked with `SELECT ... FOR UPDATE` ordered by `id ASC`.
4. **Reservation Expiry**: Expired reservations (`expires_at < NOW()`) are safely released back to available inventory via the internal maintenance operation `releaseExpiredReservations({ limit })` under `FOR UPDATE` transaction locks, without external worker dependencies.
