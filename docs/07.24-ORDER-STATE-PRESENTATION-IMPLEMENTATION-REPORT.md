# Phase 07.24 — Order State Presentation, Tracking & Payment-Recovery UI Correction Report

## Executive Summary
During local production-readiness QA of the Nexora Commerce Platform, orders with backend status `PENDING_PAYMENT` were presented in the Orders UI with the hardcoded header `"ORDER PLACED"` and actionable buttons `"Buy Again"` and `"Track Package"`. This representation was semantically false: a `PENDING_PAYMENT` order has an initiated checkout record and inventory reservation, but payment has not been authoritatively captured; fulfillment has not commenced, and package tracking is inapplicable.

Phase 07.24 executes a surgical frontend-only correction. It centralizes order-state presentation into a pure utility (`src/utils/orderStatus.js`), enforces accurate status labels and action visibility across all lifecycle states, eliminates misleading fulfillment progression on the Tracking page for unsettled orders, preserves real product image resolution, and adheres strictly to the frozen backend and payment architecture.

---

## 1. Root Cause Analysis
1. **Unconditional Header Label**:
   In `src/pages/orders/OrdersGrid.jsx`, the order card header hardcoded `<span className="order-meta-label">Order Placed</span>` for every order, irrespective of whether the order was `PENDING_PAYMENT`, `CANCELLED`, `EXPIRED`, `REFUNDED`, or `PAID`.
2. **Unconditional Action Buttons**:
   In `src/pages/orders/OrdersGrid.jsx`, every item row unconditionally rendered `Buy Again` (primary) and `Track Package` (secondary), treating all orders as placed, fulfilled, and trackable.
3. **Tracking Stepper Lumping**:
   In `src/pages/TrackingPage.jsx`, `isPending` was lumped with `isProcessing` (`isPending || isProcessing`), falsely highlighting the `"Preparing"` fulfillment step and setting a 33% progress bar width for unpaid orders.
4. **Adapter Property Parity**:
   In `src/api/adapters.js`, `adaptOrderItem` set `image` but omitted an explicit `imageUrl` property, risking fallback to placeholder assets in components or tests expecting `imageUrl`.

## 3. Action Mapping & Payment-Recovery Decision

### Payment-Recovery Decision
**NOT IMPLEMENTED — NO SAFE REUSABLE FRONTEND RECOVERY FLOW EXISTED**

### Architectural Rationale:
- The backend already provides a secure retry endpoint (`POST /api/payments/retry`), which enforces: Same Order + New PaymentAttempt + New Razorpay Order while validating active inventory reservation.
- On the frontend, Razorpay payment orchestration lives exclusively inside `CheckoutPage.jsx` (`paymentsApi.retryPayment()`, `window.Razorpay`, `paymentsApi.verifyPayment()`).
- In accordance with the prompt's explicit architectural direction, Razorpay orchestration was **not** duplicated inside `OrdersGrid.jsx`. Duplicating payment modal handlers, reconciliation states, and error handling across components would create a divergent second payment path.
- Therefore, for `PENDING_PAYMENT`:
  - `Track Package`: **Hidden**
  - `Buy Again`: **Hidden**
  - `Complete Payment`: **Not rendered in OrdersGrid**; no duplicate payment flow was invented.

## 4. Tracking Page Fulfillment Correction
In `src/pages/TrackingPage.jsx`:
- Ensured architecture-consistent response unwrapping:
  ```javascript
  const rawOrder =
    response.order ||
    response.data?.order ||
    response.data ||
    response;
  ```
- Disentangled `isPending = status === 'PENDING_PAYMENT'` from `isProcessing`.
- For `PENDING_PAYMENT`:
  - Fulfillment progress bar width is set to `0%` (`aria-valuenow="0"`).
  - None of the fulfillment steps (`Preparing`, `In Transit`, `Delivered`) are marked `active`.
  - Header displays explicit user guidance:
    `"Payment required before fulfillment tracking becomes available."`
- For terminal non-fulfillment states (`CANCELLED`, `EXPIRED`, `REFUNDED`):
  - Progress bar width is `0%`.
  - Informative status notice displayed.

## 5. Product Image Integrity

- Verified that both `PAID` and `PENDING_PAYMENT` orders render the actual product image URL (e.g. Unsplash URL) rather than falling back to `athletic-cotton-socks-6-pairs.jpg`.

- **Guest Security**: Raw guest tokens are never leaked or persisted in application logs.
- **Inventory Concurrency**: 15-minute stock reservation holds and release mechanics remain untouched.

3. **PROCESSING / SHIPPED / DELIVERED**:
   - Header shows `"ORDER PLACED"`.
   - Action buttons match expected fulfillment capabilities.
4. **CANCELLED / EXPIRED / REFUNDED**:
   - Header shows `"ORDER CANCELLED"`, `"ORDER EXPIRED"`, or `"ORDER REFUNDED"`.
   - `"Track Package"` is suppressed.
   - `"Buy Again"` allows re-ordering items.
5. **Tracking Page (`/tracking/:orderId/:productId`)**:
   - When order is `PENDING_PAYMENT`, progress bar shows `0%`, no timeline step is active, and guidance banner states `"Payment required before fulfillment tracking becomes available."`

## 12. Remaining Limitations
- While backend `POST /api/payments/retry` supports retrying payment on existing `PENDING_PAYMENT` orders, payment recovery is presently available only within the `CheckoutPage` user flow. A dedicated, unified payment-retry modal on the Orders page would require a formal shared payment recovery service across pages. In compliance with architectural instructions, no secondary payment flow was created.
