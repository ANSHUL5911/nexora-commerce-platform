## 3. Four Surgical Corrections & Behavioral Invariants

1. **Guest Tokens (Correction 1):**
   - Raw guest token, guest-token SHA-256 hash, and `X-Guest-Token` header are classified as strictly non-loggable.
   - All guest token fields (`guestToken`, `guest_token`, `guest_token_hash`, `guestTokenHash`, `x-guest-token`, `rawToken`, `tokenHash`) are sanitized to `[REDACTED]` by `redactSensitiveData`.
2. **Recursive Error & Metadata Redaction (Correction 2):**
   - Metadata fields—including `message`, `error`, `reason`, `stack`, and nested `Error` properties—pass through recursive sanitization.
   - Safe properties (`name`, `message`, `code`, `statusCode`, `stack`) are extracted from `Error` objects and stripped of sensitive tokens, DB passwords, and PANs via `sanitizeStringContent`.
3. **Cardinality & Input Boundary Control (Correction 3):**
   - Prohibits logging uncontrolled request bodies, raw inputs, customer data dumps, and query parameters.
   - HTTP paths are normalized (`req.originalUrl.split('?')[0]`).
   - Permitted correlation identifiers are strictly bounded: `orderId`, `productId`, `reservationId`, `paymentAttemptId`, `eventId`, `userId`.
4. **Verified Database Connection on Startup (Correction 4):**
   - In `server.js`, `application.started` emits `databaseConnected: true` only after `testDbConnection()` passes against PostgreSQL.
   - On connection failure, `application.startup.failed` sanitizes the error string, preventing DB credentials leakage.
5. **Behavioral Side-Effect Free Invariant:**
   - Every logger method (`info`, `warn`, `error`, `debug`) is wrapped in a fail-safe `try / catch` block.
   - If logging, JSON formatting, or standard I/O fails (e.g., broken pipe, full disk, throwing property getters), the failure is silently swallowed and the underlying commerce, payment, webhook, or authentication transaction executes normally.

## 7. Payment Authority & AuditLog Boundary Verification

### Payment Authority
1. **Frontend Callbacks are Non-Authoritative:** Frontend Razorpay handler callback sends payment payload to backend `/api/payments/verify`. Backend never marks an order paid on frontend claims.
2. **Backend Verification is Reconciliation:** Backend independently verifies the cryptographic HMAC-SHA256 signature using `config.RAZORPAY_KEY_SECRET`.
3. **Verified Captured Payment/Webhook is Authoritative:** Settlement is triggered only when verification passes or a cryptographically verified webhook is received.
4. **`settleCapturedPayment` is the Settlement Boundary:** Enclosed in a PostgreSQL transaction with row locks (`LOCK.UPDATE`), ensuring single settlement, inventory conversion, and idempotency completion.

### AuditLog vs. Operational Logging Separation
- **`AuditLog` Model (PostgreSQL):** Stores compliance and security evidence (`action`, `actor_id`, `target_resource`, `resource_id`, `ip_address`, `details_json`). For session correlation, session SIDs are stored as SHA-256 hashes (`hashSessionId(sid)`), never plain text.
- **Operational Logs (`logger`):** Technical JSON logs streamed to `stdout`/`stderr` for monitoring and debugging. Never stored in PostgreSQL tables.

## 8. Manual Scenario Trace Verifications (Scenarios A through G)

- **Scenario A (Customer Checkout):** `POST /api/orders` (`idempotency.claimed` -> `inventory.reservation.created` -> `order.created`) -> `POST /api/payments/initiate` (`payment.attempt.created` -> `payment.gateway.order.created`) -> `POST /api/payments/verify` (`payment.verification.started` -> `payment.capture.confirmed` -> `inventory.reservation.converted` -> `payment.settlement.completed` -> `order.status_changed`).
- **Scenario B (Guest Checkout):** `POST /api/orders` unauthenticated -> `order.created` (`isGuest: true`, returns token in body, never in logs) -> `GET /api/orders/:id` with `X-Guest-Token` header redacted -> `GET /api/orders/:id` with invalid token logs `guest.token.invalid` without token metadata.
- **Scenario C (Failed Payment):** Invalid HMAC signature logs `payment.signature.invalid` without signature string -> order remains `PENDING` -> retry logs `payment.attempt.created` (`attemptNumber: 2`) -> succeeds non-destructively.
- **Scenario D (Webhook Idempotency):** Inbound `payment.captured` logs `webhook.processing.started` -> verified -> `payment.settlement.completed` -> `webhook.processing.completed`. Duplicate webhook logs `webhook.duplicate` and drops safely.
- **Scenario E (Inventory Concurrency):** Exhausted stock logs `inventory.insufficient_stock` (`productId`, `requestedQuantity`, `availableQuantity`) without corruption.
- **Scenario F (Admin Refund):** `POST /api/admin/orders/:id/refund` logs `admin.refund.requested` -> gateway called outside DB tx -> `admin.refund.completed` -> stock untouched (`REFUND != RESTOCK`).
- **Scenario G (Admin Restock):** `POST /api/admin/orders/:id/restock` logs `admin.restock.requested` -> stock restored under row locks -> `admin.restock.completed`.
