# Phase 07.23 — Login-Required Checkout Architecture Decision

## 1. Executive Summary & Product Decision
This document records a deliberate, controlled **product requirement change** for the Nexora Commerce Platform. 

Previously, under Phase 07.11 (`docs/07.11-GUEST-CHECKOUT-IMPLEMENTATION-REPORT.md`), the platform allowed unauthenticated guests to navigate directly through checkout to payment (`Guest → Cart → Checkout → Payment`). 

By explicit product decision during local production-readiness QA, the checkout entry path is transitioned to:
**Login-Required Checkout** (`Guest → Browse → Guest Cart → Cart → Login/Register → Checkout → Payment`).

> [!IMPORTANT]
> **Controlled Product Change, Not a Security Bypass:**
> This change is an intentional product design decision. It is **NOT** a mechanism to bypass, disable, or weaken CSRF defenses. The Double-Submit Cookie CSRF architecture (`nexora_csrf` cookie + `x-csrf-token` header) is fundamentally correct for authenticated state-changing operations. Requiring authentication before entering checkout aligns the entry point with established session and CSRF provisioning.

---

## 2. Comparative User Flows

### Previous Flow (Phase 07.11 Guest Checkout)
```
Guest → Product Discovery → Guest Cart → Cart → /checkout → Order Creation (Unauthenticated) → Razorpay
```
- Allowed anonymous order creation (`userId: null`) with raw `guestToken` generation.
- Encountered unauthenticated CSRF barriers because `nexora_csrf` was provisioned only upon login/register.

### New Flow (Phase 07.23 Login-Required Checkout)
```
Guest
  ↓
Product Discovery (Catalog, Search, Product Details)
  ↓
Guest Cart (localStorage: nexora_guest_cart)
  ↓
Cart Page (/cart)
  ↓
"Proceed to Checkout" Clicked
  ↓
Authentication Gate (Modal / Inline Gate)
  ├── Existing User: Sign In
  └── New User: Create Account
        ↓
Session & CSRF Established (Cookie: nexora_csrf, Session: nexora_sid)
  ↓
Guest Cart Preserved & Migrated (POST /api/cart/items server-side)
  ↓
Checkout Flow (/checkout)
  ├── 1. Delivery Address
  ├── 2. Shipping Method
  ├── 3. Order Review & Reservation
  └── 4. Razorpay Payment (POST /api/payments/create-order)
        ↓
Authoritative Webhook / Verification Reconciliation
```

## 3. Boundary Definitions & Guest Capabilities

### Guests MAY:
- Browse the full product catalog and category filters.
- Perform debounced live search.
- View individual product detail pages, prices, and stock indicators.
- Add items to the guest cart (`nexora_guest_cart` in `localStorage`).
- Adjust quantities in the guest cart.
- Remove items or clear the guest cart.
- View the cart page (`/cart`).

### Guests MUST NOT:
- Enter the active checkout flow (`/checkout`).
- Initiate an ecommerce `Order`.
- Create an `InventoryReservation`.
- Create a `PaymentAttempt`.
- Create a Razorpay Order.
- Initiate payment.
- Access authenticated checkout or cart APIs.

## 4. Authentication Gate & Direct Route Protection

### 4.1 Cart Page Gate
When an unauthenticated user on `/cart` clicks **"Proceed to Checkout"**:
1. Navigation to `/checkout` is blocked.
2. The `AuthModal` appears with an explicit subtitle:
   > *"Create an account or sign in to continue to checkout."*
3. Upon successful login or registration, the guest cart items are transferred to the user's server cart, and the user is seamlessly transitioned directly to `/checkout`.

### 4.2 Direct `/checkout` Protection
If an unauthenticated guest directly enters `/checkout` in the browser address bar:
1. **Session Verification State**: While `authLoading === true`, the application renders an accessible status indicator (`Verifying Session`) and does **not** prematurely classify the visitor as a guest or initiate redirect loops.
2. **Authentication Gate**: When `authLoading === false` and `currentUser === null`, the page displays the authentication gate card:
   - Heading: `Sign in to continue`
   - Description: `Create an account or sign in to continue to checkout.`
   - Actions: `[Sign In]` and `[Create Account]`
3. No checkout initiation (`POST /api/checkout/initiate`), stock reservation, or payment order calls are permitted.

## 5. Guest Cart Preservation Architecture

A critical user experience mandate is that **cart contents must not be lost upon authentication**.

### Mechanism:
1. **Client Storage**: The guest cart remains stored in `localStorage` under `nexora_guest_cart` as a minimal array:
   ```json
   [
     { "productId": "uuid-here", "quantity": 1 }
   ]
   ```
   No prices, stock, totals, session IDs, or tokens are stored locally.
2. **Authentication Transfer**: Upon successful login or registration (`handleAuthChange`):
   - The frontend reads `getGuestCart()`.
   - Each item is added to the authenticated user's cart via the existing `cartApi.addItem({ productId, quantity })` (`POST /api/cart/items`).
   - The backend validates stock availability, computes authoritative prices, and binds items to the authenticated customer session.
   - `clearGuestCart()` is called to purge `localStorage` only after server-side ingestion succeeds.
3. **No Redundant Merge API**: Uses existing, tested server-side cart endpoints without creating redundant endpoints or mutating databases directly from the client.

## 6. Security, CSRF & Payment Verification

### 6.1 CSRF Enforcement Remains 100% Intact
- **Zero Weakening**: CSRF middleware is **not** disabled, bypassed, or exempted.
- **Tokens**: The Double-Submit cookie pattern remains strictly enforced:
  - Cookie: `nexora_csrf` (HTTP-only flag false, SameSite=Lax, Path=/)
  - Header: `x-csrf-token` (read from cookie and sent on all mutations)
- **Automatic Provisioning**: Successful login/registration provisions the `nexora_csrf` cookie, allowing subsequent authenticated state-changing requests to satisfy the existing Double-Submit CSRF validation.

### 6.2 Payment Authority
- **Non-Authoritative Client**: Frontend Razorpay handlers remain strictly non-authoritative presentation triggers.
- **Backend Settle Authority**: Payment transitions to `PAID` exclusively occur through `POST /api/payments/verify` or the authoritative webhook handler (`POST /api/webhooks/razorpay`), executing `settleCapturedPayment()` with database transactions and inventory conversion.

### 6.3 Guest-Token Infrastructure
- The existing guest-token infrastructure (cryptographic hash generation, token storage, and legacy lookup) is **not deleted**.
- It remains available for historical guest orders, order lookup endpoints (`GET /api/orders/guest/:orderId`), and regression tests.
- For new checkouts originating from the UI, checkout requests are now authenticated customer requests (`req.user.id`).

## 7. Backend, Database & Migration Audit

- **Backend Code Changes**: **0 lines changed**.
- **Backend Route Authorization Mapping**:
  - `/api/cart`: Enforces `requireAuth` and `verifyCsrf` on all routes (`/`, `/items`, `/items/:itemId`). Unauthenticated requests are rejected with HTTP 401 `AUTHENTICATION_REQUIRED`.
  - `/api/checkout/initiate`: Configured with `optionalAuth`, `verifyCsrf`, `checkoutLimiter`, and `requireIdempotency`. The backend technically retains the Phase 07.11 guest order branch (`orderService.createGuestOrder`) if an `items` payload is provided, but strictly enforces Double-Submit CSRF validation. The frontend product gate now strictly prevents unauthenticated access from reaching this endpoint.
  - `/api/payments/create-order`, `/retry`, `/verify`: Configured with `requireAuthOrGuestToken`, `checkoutLimiter`, `verifyCsrf`, and `requireIdempotency`. Anonymous requests without an `X-Guest-Token` are rejected with HTTP 401 `AUTHENTICATION_REQUIRED`.
- **Database Schema Changes**: **None**.
- **Database Migrations**: **None**.
- **Dependencies**: **None added or updated**.
