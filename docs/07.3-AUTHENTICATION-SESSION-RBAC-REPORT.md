## 1. Executive Summary & Scope

Phase 07.3 establishes the enterprise-grade authentication, authorization, session management, and anti-CSRF security foundation for the Nexora Commerce Platform. The implementation strictly adheres to frozen specifications `01-PRD-v2.1.md`, `02-TRD-v1.2.1.md`, `05-BACKEND-SCHEMA-v1.0.md`, `06-IMPLEMENTATION-PLAN-v1.0.md`, and `07.0-IMPLEMENTATION-BASELINE.md`.

### Implemented Security & Authentication Capabilities:
- **Server-Side Session Store in PostgreSQL:** Opaque 256-bit CSPRNG session identifiers (`crypto.randomBytes(32).toString('hex')`) persisted in the `sessions` table.
- **Zero JWT / Bearer / Token Leaks:** Absolute exclusion of JWTs, localStorage access tokens, OAuth flows, and client-side token stores.
- **Strict Cookie Security Architecture:** `__Host-nexora_sid` (production) / `nexora_sid` (dev/test) cookie flag enforcement (`HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure=true` in production, zero `Domain` attribute).
- **Bcrypt Password Security:** Cost factor 12 hashing with timing-attack mitigation (dummy hash verification on nonexistent user lookup to normalize response latency across valid and invalid identities).
- **Session Fixation Defense:** Full session destruction and new opaque token generation upon every login and registration event.
- **Rolling Session Renewal:** 7-day TTL with race-safe atomic conditional database updates when remaining lifetime $\le 6$ days (`WHERE sid = :sid AND expires_at > NOW()`).
- **CSRF Double-Submit Protection:** Cryptographically secure `nexora_csrf` cookie matched against `X-CSRF-Token` header using `crypto.timingSafeEqual()`, bypassing safe methods (`GET`, `HEAD`, `OPTIONS`) and isolating `/api/webhooks/*` boundaries.
- **Role-Based Access Control (RBAC):** Server-side `requireRole(['admin'])` and `requireAdmin` middlewares backed by database `role` values (`customer`, `admin`).
- **Insecure Direct Object Reference (IDOR) Defense:** Formalized `assertOwnerOrAdmin(reqUser, targetUserId)` helper preventing horizontal privilege escalation.
- **Safe DTO Serialization:** `toSafeUserDTO` serializer guaranteeing `password_hash` and sensitive attributes never reach API responses.
- **Authentication Rate Limiting:** 5 requests per minute per IP rate limiter on all `/api/auth/*` routes.
- **Application-Side UUID Generation:** Node.js `crypto.randomUUID()` used across all entities, adhering to Phase 07.2 zero-pgcrypto / zero-`gen_random_uuid()` database strategy.

## 3. Architectural Design & Security Guarantees

```
                                      +-------------------------------------------------------+
                                      |                    CLIENT BROWSER                     |
                                      +-------------------------------------------------------+
                                            |                                   ^
       POST /api/auth/login                 |                                   |  Set-Cookie: __Host-nexora_sid (HttpOnly)
       (email, password)                    |                                   |  Set-Cookie: nexora_csrf (JS-readable)
                                            v                                   |  200 OK + { user: safeUserDTO }
                               +-------------------------------------------------------+
                               |                 EXPRESS BACKEND (PORT 5000)           |
                               +-------------------------------------------------------+
                                     |  1. authLimiter (5 req/min/IP)
                                     |  2. Zod Request Body Validation
                                     |  3. Lookup user & compare bcrypt hash (cost 12)
                                     |     (runs dummy bcrypt on non-existent user)
                                     |  4. Rotate & create new 256-bit CSPRNG session
                                     |  5. Write AuditLog entry
                                     v
                               +-------------------------------------------------------+
                               |             POSTGRESQL DATABASE (PORT 5432)           |
                               |                     (nexora_dev)                      |
                               +-------------------------------------------------------+
                               |  - users (id UUID PK, email UNIQUE, password_hash)    |
                               |  - sessions (sid VARCHAR(64) PK, user_id FK, expires)  |
                               |  - audit_logs (id UUID PK, action, user_id, metadata) |
                               +-------------------------------------------------------+
```

### 3.1 Strict Exclusion of JWTs
Nexora adheres to a strict server-side session architecture:
- **Zero JWT / Bearer Tokens:** No JWT signing keys, no client-side token storage in `localStorage` or `sessionStorage` (preventing XSS-based token exfiltration).
- **Zero OAuth:** Excluded per PRD/TRD specification; authentication is strictly email/password with server-side validation.
- **Instant Revocation:** Sessions can be revoked immediately in PostgreSQL upon logout or security compromise, unlike stateless JWTs which require complex revocation blocklists.

### 3.2 Opaque Session Tokens & PostgreSQL Session Store
- **Entropy:** Session IDs (`sid`) are 256-bit (32-byte) cryptographically secure pseudorandom numbers generated via Node.js `crypto.randomBytes(32).toString('hex')` (64 hexadecimal characters, yielding $\approx 1.15 \times 10^{77}$ combinations).
- **Persistence:** Stored in the `sessions` table created in Phase 07.2 Migration `002_create_users_and_sessions.cjs`.
- **Default TTL:** 7 days (`604,800,000` ms) configured via `SESSION_MAX_AGE_MS`.
- **Race-Safe Rolling Expiration:** When an authenticated request arrives and the session has less than 6 days of remaining TTL (`expires_at - NOW() <= 6 days`), the backend executes an atomic conditional update:
  ```sql
  UPDATE sessions 
  SET expires_at = :newExpiry, updated_at = NOW() 
  WHERE sid = :sid AND expires_at > NOW();
  ```
  This eliminates database write amplification on every HTTP read while maintaining active sessions without race condition vulnerabilities.

### 3.3 Cookie Security Architecture
Authentication and CSRF tokens are transported exclusively via HTTP cookies configured with defense-in-depth flags:

| Cookie Name | Scope | HttpOnly | Secure | SameSite | Path | Domain | Description |
|---|---|---|---|---|---|---|---|
| `__Host-nexora_sid` | Production | `true` | `true` | `Lax` | `/` | *None* | Opaque session token. `__Host-` prefix enforces HTTPS and prevents subdomain hijacking. |
| `nexora_sid` | Dev / Test | `true` | `false` | `Lax` | `/` | *None* | Fallback name for non-HTTPS local development and testing environments. |
| `nexora_csrf` | All Envs | `false` | `true` (prod) | `Lax` | `/` | *None* | Anti-CSRF double-submit token. Readable by frontend JavaScript to populate `X-CSRF-Token` header. |

## 4. Password Security & Timing Mitigation

### 4.1 Bcrypt Cost Factor 12
All user passwords are encrypted using `bcryptjs` with cost factor 12 ($2^{12} = 4,096$ iterations), providing robust defense against offline GPU/ASIC brute-force attacks while maintaining sub-300ms login response times.

### 4.2 Dummy Hash Timing Attack Mitigation
To prevent user enumeration via timing discrepancies between existing and non-existing accounts, the password service generates a static precomputed dummy hash at application startup. When a login request specifies an email not present in PostgreSQL, the backend verifies the provided password against the dummy hash, equalizing the CPU workload before returning a generic `401 Unauthorized` (`INVALID_CREDENTIALS`).

```javascript
// Module: ecommerce-backend/src/modules/auth/password.js
const DUMMY_HASH = bcrypt.hashSync('nexora-dummy-timing-mitigation-pass', 12);

export async function verifyPassword(plainPassword, hashedPassword) {
  return bcrypt.compare(plainPassword, hashedPassword);
}

export async function verifyPasswordWithDummy(plainPassword) {
  return bcrypt.compare(plainPassword, DUMMY_HASH);
}
```

## 5. CSRF Protection (Double-Submit Pattern)

To secure state-mutating requests against Cross-Site Request Forgery:
1. **Token Generation:** Upon registration, login, or initial authentication, a 256-bit CSPRNG token (`crypto.randomBytes(32).toString('hex')`) is issued in the `nexora_csrf` cookie.
2. **Frontend Submission:** Single-Page Applications or API clients read the cookie and submit the value in the `X-CSRF-Token` HTTP header on all state-mutating requests (`POST`, `PUT`, `PATCH`, `DELETE`).
3. **Timing-Safe Comparison:** The backend middleware compares the cookie token and header token using `crypto.timingSafeEqual()`:
   ```javascript
   const cookieBuf = Buffer.from(cookieToken);
   const headerBuf = Buffer.from(headerToken);
   if (cookieBuf.length !== headerBuf.length || !crypto.timingSafeEqual(cookieBuf, headerBuf)) {
     throw new ForbiddenError('Invalid CSRF token.', 'CSRF_INVALID');
   }
   ```
4. **Bypass Rules:**
   - Safe HTTP methods (`GET`, `HEAD`, `OPTIONS`) bypass CSRF verification.
   - Payment provider webhook endpoints matching `/api/webhooks/*` are explicitly exempted from CSRF verification (relying instead on Phase 07.6 HMAC-SHA256 signature verification).

## 6. Role-Based Access Control (RBAC) & IDOR Defense

### 6.1 Server-Side Role Enforcement
The `users` table enforces roles via PostgreSQL `CHECK (role IN ('customer', 'admin'))`. The backend provides centralized middleware guards:
- `requireRole(['admin'])`: Enforces that `req.user` possesses one of the allowed roles, throwing `403 Forbidden` (`INSUFFICIENT_PERMISSIONS`) if unauthorized.
- `requireAdmin`: Convenient alias for admin-only operations.

### 6.2 IDOR Defense Helper (`assertOwnerOrAdmin`)
To prevent Insecure Direct Object Reference vulnerabilities across user-scoped resources (e.g., profile, addresses, orders):
```javascript
// Module: ecommerce-backend/src/modules/auth/rbac.middleware.js
export function assertOwnerOrAdmin(reqUser, targetUserId) {
  if (!reqUser) {
    throw new AuthenticationError('Authentication required.', 'AUTHENTICATION_REQUIRED');
  }
  if (reqUser.role === 'admin') {
    return true;
  }
  if (reqUser.id === targetUserId) {
    return true;
  }
  throw new ForbiddenError('You do not have permission to access this resource.', 'FORBIDDEN_RESOURCE');
}
```

## 7. API Endpoints Specification

### 7.1 `POST /api/auth/register`
Creates a new customer account, establishes an active server session, and issues session & CSRF cookies.
- **Rate Limit:** 5 requests / min / IP.
- **Request Body:**
  ```json
  {
    "email": "customer@example.com",
    "password": "SecurePassword123!",
    "full_name": "Aarav Sharma",
    "phone": "+91-XXXXXXXXXX"
  }
  ```
- **Responses:**
  - `201 Created`: Returns `{ "status": "success", "data": { "user": { "id": "...", "email": "...", "full_name": "...", "role": "customer", "phone": "..." } } }` with `Set-Cookie: __Host-nexora_sid` and `Set-Cookie: nexora_csrf`.
  - `400 Bad Request`: Validation failure (e.g., invalid email format, password < 8 characters).
  - `409 Conflict`: Email already registered (`EMAIL_ALREADY_EXISTS`).

### 7.2 `POST /api/auth/login`
Authenticates credentials, rotates session ID to eliminate session fixation, and issues new cookies.
- **Rate Limit:** 5 requests / min / IP.
- **Request Body:**
  ```json
  {
    "email": "customer@example.com",
    "password": "SecurePassword123!"
  }
  ```
- **Responses:**
  - `200 OK`: Returns `{ "status": "success", "data": { "user": { ... } } }` with rotated session cookies.
  - `401 Unauthorized`: Generic `INVALID_CREDENTIALS` for nonexistent user or invalid password.

### 7.3 `GET /api/auth/me`
Fetches the sanitized profile of the currently authenticated user.
- **Headers:** `Cookie: __Host-nexora_sid=<sid>`
- **Responses:**
  - `200 OK`: Returns `{ "status": "success", "data": { "user": { ... } } }`.
  - `401 Unauthorized`: Missing, expired, or invalid session (`AUTHENTICATION_REQUIRED`).

### 7.4 `POST /api/auth/logout`
Destroys the server-side session in PostgreSQL and clears all authentication and CSRF cookies.
- **Headers:** `Cookie: __Host-nexora_sid=<sid>`, `X-CSRF-Token: <csrf_token>`
- **Responses:**
  - `200 OK`: Returns `{ "status": "success", "message": "Successfully logged out." }`.

## 8. Security Threat Model & Mitigations

| Threat Vector | Severity | Mitigating Architecture |
|---|---|---|
| **Session Hijacking via XSS** | Critical | Opaque session IDs stored strictly in `HttpOnly` cookies. Never exposed to document scripts or JavaScript APIs. |
| **Session Fixation** | High | `sessionService.rotateSession()` destroys existing pre-login sessions and provisions new 256-bit CSPRNG tokens on every login/registration. |
| **Cross-Site Request Forgery (CSRF)** | High | Double-submit cookie verification with `crypto.timingSafeEqual()` on all state-mutating HTTP methods (`POST`, `PUT`, `PATCH`, `DELETE`). |
| **Horizontal Privilege Escalation (IDOR)** | High | `assertOwnerOrAdmin` guarantees customers can only access their own records while admins retain global authority. |
| **Brute Force & Credential Stuffing** | High | IP-scoped rate limiter enforcing 5 requests / min window on all `/api/auth/*` endpoints. |
| **User Enumeration via Timing** | Medium | Non-existent user lookups execute dummy bcrypt cost-12 hashing to equalize latency with valid user password comparisons. |
| **User Enumeration via Error Messages** | Medium | Registration returns clean `409` conflict without leaking account metadata; login returns identical `INVALID_CREDENTIALS` for unknown email or wrong password. |
| **Sensitive Field Leakage** | Critical | Sequelize default scope excludes `password_hash`; `toSafeUserDTO()` explicitly whitelists safe presentation fields. |
| **Database Bloat from Inactive Sessions** | Low | Expired sessions are rejected on lookup; rolling refresh threshold prevents high-frequency database writes on active sessions. |
