## 1. Executive Summary

Phase 07.12 implements administrative full payment refunds and explicit physical inventory restocking for the Nexora Commerce Platform. The subsystem strictly adheres to the core business rule: **`REFUND != RESTOCK`**. A successful payment refund transitions financial and order state to `REFUNDED` while leaving `Product.stock_quantity` and `Product.reserved_quantity` untouched. Physical restocking is decoupled into an explicit, authenticated administrative operation executed only after physical return verification.

### Core Guarantees Delivered
1. **Strict Decoupling of Financial Refunds and Inventory Restocking (`REFUND != RESTOCK`)**:
   - `POST /api/admin/orders/:orderId/refund` settles full gateway refund via Razorpay, transitioning Order and PaymentAttempt to `REFUNDED`, while keeping product stock quantities identical.
   - `POST /api/admin/orders/:orderId/restock` allows administrators to physically restock items into sellable inventory on verified `REFUNDED` orders.
2. **Idempotent Refund Execution & Anti-Double-Refund Protection**:
   - Integrated with Phase 07.10 idempotency infrastructure (`Idempotency-Key` header, canonical request fingerprinting).
   - Multi-phase transaction architecture prevents duplicate Razorpay gateway calls under network retries, crashes, or concurrent administrative requests.
3. **Safe External Gateway Transaction Boundary**:
   - Database locks are never held open across external Razorpay HTTP operations.
   - Ambiguous gateway outcomes cleanly record failure/recovery status without blind duplicate refund attempts.
4. **Physical Restock Bounds & Anti-Double-Restock Mathematics**:
   - Restocking verifies remaining restockable quantity per item: `remaining = ordered_quantity - already_restocked_quantity`.
   - Rejects over-restocking, duplicate restocks, or foreign product injections.
5. **Multi-Product Atomic Restocking with Ascending UUID Locking**:
   - Product rows are acquired and locked using `FOR UPDATE` in ascending UUID order, completely preventing PostgreSQL deadlocks.
   - All product stock updates, `StockRestockLogs`, and `AuditLogs` succeed or roll back atomically in a single transaction.
6. **Robust Anti-IDOR & Admin RBAC**:
   - Full enforcement of `requireAuth`, `requireAdmin`, and `verifyCsrf`. Regular customers and guest sessions receive sanitized `403 FORBIDDEN` / `401 UNAUTHENTICATED` responses.
   - Actor identity is derived strictly from the verified session context (`req.user.id`).

### Lifecycle & State Transitions
```
                [ Admin POST /api/admin/orders/:id/refund ]
                                     │
                                     ▼
                      [ RBAC + CSRF + Idempotency ]
                                     │
                                     ▼
                ┌─────────────────────────────────────────┐
                │ Phase A: DB Transaction & Pre-Check     │
                │ - Lock Order & PaymentAttempt (FOR UPDATE)
                │ - Verify Order status in (PAID, PROCESSING)
                │ - Verify PaymentAttempt status = SUCCESS
                │ - Transition state to REFUND_PENDING / IN_PROGRESS
                │ - Commit Phase A Transaction           │
                └────────────────────┬────────────────────┘
                                     │
                                     ▼
                ┌─────────────────────────────────────────┐
                │ Phase B: External Gateway Call          │
                │ - Call razorpayGateway.refundPayment()   │
                │ - No DB locks held during HTTP call     │
                └────────────────────┬────────────────────┘
                                     │
                     ┌───────────────┴───────────────┐
                     │                               │
             [ Gateway Success ]             [ Gateway Failure ]
                     │                               │
                     ▼                               ▼
      ┌─────────────────────────────┐ ┌─────────────────────────────┐
      │ Phase C: Finalize Refund    │ │ Rollback & Record Error     │
      │ - PaymentAttempt -> REFUNDED│ │ - Revert PaymentAttempt     │
      │ - Persist razorpay_refund_id│ │ - Record safe error logs    │
      │ - Order -> REFUNDED         │ │ - Rollback idempotency      │
      │ - Stock Quantity: UNCHANGED │ │ - Stock: UNCHANGED          │

      └─────────────────────────────┘
```

## 4. Razorpay Integration

The Razorpay gateway adapter (`razorpay.gateway.js`) encapsulates external communication with the Razorpay Payments API:
- Method: `refundPayment({ paymentId, amountPaise, notes, speed })`
- Calls `razorpay.payments.refund(paymentId, { amount, notes, speed })` with integer paise.
- Masks sensitive credentials and transforms upstream errors into sanitized `RazorpayGatewayError` objects without exposing secrets or stack traces.

## 5. Refund Idempotency

Refunds utilize the Phase 07.10 idempotency architecture:
- **Header**: `Idempotency-Key` is required on `POST /api/admin/orders/:orderId/refund`.
- **Pre-claiming**: Atomic claiming with SHA-256 fingerprint validation (`userId + method + path + sorted(body)`).
- **Replay**: Identical requests replay the original status code, headers, and cached response payload.
- **Payload Mismatch**: Modified request payloads with the same key receive HTTP `409 IDEMPOTENCY_PAYLOAD_MISMATCH`.

---

## 6. Refund Concurrency

Under concurrent administrative refund attempts:
- PostgreSQL row-level locks (`SELECT ... FOR UPDATE`) in Phase A ensure that only the first winning transaction claims the refundable state.
- All competing concurrent requests encounter an already transitioned or non-refundable state and return HTTP `409 ALREADY_REFUNDED` / `422 ORDER_NOT_REFUNDABLE`.
- Verified under real PostgreSQL concurrency tests (2 concurrent and 10 concurrent racers) resulting in **exactly 1 Razorpay refund call** and 0 duplicate settlements.

## 8. Inventory Invariants

Physical restocking maintains strict database and mathematical invariants:
1. `stock_quantity >= 0` (guaranteed by check constraint `chk_product_stock_quantity_non_negative`).
2. `reserved_quantity >= 0` (guaranteed by check constraint `chk_product_reserved_quantity_non_negative`).
3. `reserved_quantity <= stock_quantity` (guaranteed by check constraint `chk_product_reserved_lte_stock`).
4. `available_quantity = stock_quantity - reserved_quantity`.
5. Restocking strictly increments `stock_quantity` without altering `reserved_quantity`.
6. Total restocked quantity per order item is mathematically capped: `SUM(StockRestockLog.quantity) <= OrderItem.quantity`.

---

## 9. Audit Logging

Every administrative refund and restock action writes an immutable audit trail entry:
- **Refund Audit**: Records `actor_id` (admin UUID), `action: 'REFUND_ORDER'`, `target_id: orderId`, `metadata: { orderId, paymentAttemptId, amountPaise, currency, razorpayRefundId }`.
- **Restock Audit**: Records `actor_id` (admin UUID), `action: 'RESTOCK_ORDER'`, `target_id: orderId`, `metadata: { orderId, itemsRestocked, reason }`.
- **StockRestockLog**: Records per-product physical restock logs linking `order_id`, `product_id`, `quantity`, `reason`, and `created_by`.

## 10. Security / RBAC / Anti-IDOR

1. **Role-Based Access Control**:
   - Unauthenticated callers: HTTP `401 UNAUTHENTICATED`.
   - Regular customer sessions: HTTP `403 INSUFFICIENT_PERMISSIONS`.
   - Guest checkout tokens: HTTP `403 INSUFFICIENT_PERMISSIONS`.
   - Only validated `admin` roles can access `/api/admin/*` endpoints.
2. **CSRF Protection**:
   - Enforces `verifyCsrf` on all state-mutating admin routes via the `nexora_csrf` cookie and `x-csrf-token` header.
3. **Anti-IDOR Protections**:
   - Order IDs in path parameters are strictly validated and looked up server-side.
   - PaymentAttempts are derived authoritatively from database relationships; client-supplied payment attempt IDs or refund amounts are rejected.
   - Product IDs in restock requests must match items present on the target order snapshot.

## 13. PostgreSQL Concurrency Evidence

Real PostgreSQL concurrency test executions against the `nexora_test` database:
1. **Concurrent Refund Race (10 simultaneous requests)**:
   - 10 parallel HTTP POST requests with different idempotency keys targeting the same paid order.
   - Result: Exactly 1 request received HTTP 200 OK. 9 requests received HTTP 409 / 422 conflict.
   - Exactly 1 Razorpay gateway call executed. Stock remained unchanged.
2. **Concurrent Restock Race (10 simultaneous requests)**:
   - 10 parallel HTTP POST restock requests targeting the same refunded order item of quantity 2.
   - Result: Exactly 1 request successfully claimed the restock. Competing requests were rejected with `RESTOCK_QUANTITY_EXCEEDED` / `ALREADY_RESTOCKED`.
   - Final product stock increased by exactly 2 (no double-increment, no overshoot, zero lost updates).
