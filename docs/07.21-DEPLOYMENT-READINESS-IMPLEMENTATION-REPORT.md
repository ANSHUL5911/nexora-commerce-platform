## 1. Executive Summary

Phase 07.21 transitions the Nexora Commerce Platform from performance verification into **Production Deployment Readiness**. Rather than assuming cloud viability because localhost and test suites function, this phase performed a comprehensive, multi-dimensional audit of the platform's configuration contracts, secret handling, startup lifecycles, database connectivity, CORS/cookie/CSRF cross-origin policies, reverse-proxy awareness, and fail-safe recovery procedures.

Five critical deployment blockers and two operational recommendations were identified and resolved with minimal, surgical changes:
1. **CORS Preflight Hardening**: Added `X-CSRF-Token` to CORS `allowedHeaders` in `src/middleware/cors.js` to ensure cross-origin browser preflight requests succeed on split-origin cloud deployments (e.g., `app.nexora.com` → `api.nexora.com`).
2. **Frontend API Origin Flexibility**: Updated `ecommerce-project/src/api/client.js` to configure `baseURL` dynamically from `import.meta.env.VITE_API_BASE_URL` (defaulting to `/api`) and removed hardcoded `localhost:5000` assumptions.
3. **Database URL Precedence & Validation**: Added native `DATABASE_URL` connection string parsing and validation to `src/config/env.js` and `src/config/database.js` with strict precedence over discrete database variables (`DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD`), while enforcing fail-fast validation in production.
4. **Strict `TRUST_PROXY` Validation**: Implemented safe, strict parsing for Express `trust proxy` configuration in `src/config/env.js` and `src/app.js`, rejecting unsafe or arbitrary proxy strings, and updated all rate limiters to rely on authenticated `req.ip` rather than unverified raw `X-Forwarded-For` headers.
5. **Operational Health & Readiness Endpoints**: Mounted `/api/health` (liveness) and `/api/health/ready` (readiness with safe `sequelize.authenticate()`) prior to the general API rate limiter to prevent orchestrator/load balancer health check exhaustion, ensuring zero leakage of database credentials, SQL, or stack traces on failure (returning sanitized 503).
6. **Cookie Invalidation Security Flags**: Hardened `clearAuthCookies` and stale session clearing in `auth.controller.js` and `auth.middleware.js` to explicitly pass `secure: true`, `path: '/'`, and `httpOnly` flags matching RFC 6265bis specifications for `__Host-` prefixed cookies.
7. **Production Fail-Fast & Timeout-Guarded Shutdown**: Enforced immediate fail-fast termination (`process.exit(1)`) on database connection failure during production startup, and implemented an explicit 10-second safety timeout in `server.js` graceful shutdown to prevent hanging processes during container termination.

## 4. Deployment Topology

Nexora supports two provider-neutral production topologies:

```
TOPOLOGY A: Unified Reverse Proxy (Same-Origin)
===================================================
Browser (Client)
      │
      ▼ HTTPS
[ Reverse Proxy / CDN / CloudFront / Nginx / ALB ]
      ├── /api/*      ──► [ Node.js Backend Server :5000 ]
      │                         │
      │                         ▼
      │                   [ PostgreSQL 16+ Managed DB ]
      │
      └── /* (Static) ──► [ Frontend Static Assets / SPA (dist/) ]


TOPOLOGY B: Split-Origin Cloud Architecture
===================================================
Browser (Client)
      │
      ├──── HTTPS ────► [ Frontend CDN: https://app.nexora.com ]
      │                         │ (Static SPA HTML/JS/CSS)
      │
      └──── HTTPS ────► [ Backend API: https://api.nexora.com ]
                                │ (Node.js Express + Helmet + Strict CORS)
                                ▼
                        [ PostgreSQL 16+ Managed DB ]
```

Both topologies enforce:
- Strict CORS validation (`CORS_ORIGIN`).
- Double-submit CSRF cookie + header (`X-CSRF-Token`).
- `__Host-nexora_sid` session cookies (`Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`).
- Webhook signature validation (`POST /api/webhooks/razorpay`) directly from Razorpay servers.

### Recommended Backup Policy

   - Recovery Point Objective (RPO): < 5 minutes (via WAL streaming).
   - Recovery Time Objective (RTO): < 30 minutes (via managed snapshot restore).

## 11. Graceful Shutdown Sequence

Signal handlers for `SIGTERM` and `SIGINT` in `server.js` execute a deterministic shutdown sequence:

```
[ SIGTERM / SIGINT Received ]
             │
             ▼
  [ 1. Start 10-Second Safety Timer (unref'd) ]
             │
             ▼
  [ 2. Stop Accepting New Connections (server.close()) ]
             │
             ▼
  [ 3. Allow Active HTTP Requests to Complete Drain ]
             │
             ▼
  [ 4. Close PostgreSQL Connection Pool (sequelize.close()) ]
             │ (In-flight DB transactions either complete or roll back safely)
             ▼
  [ 5. Clear Timer & Clean Exit (process.exit(0)) ]

* If total shutdown duration exceeds 10 seconds:
  Log fatal shutdown timeout event & force process exit (process.exit(1))
```

**Payment & Webhook Safety**: The shutdown process never forcibly aborts active database transactions; transactions either commit or roll back safely under PostgreSQL ACID guarantees.

## 12. Authentication & Cookie Security

- **Session Authority**: Server-side PostgreSQL sessions indexed by opaque 64-hex identifiers.
- **Production Cookie Settings**:
  - Name: `__Host-nexora_sid`
  - `HttpOnly: true` (inaccessible to JavaScript)
  - `Secure: true` in production
  - `SameSite: 'lax'`
  - `Path: '/'`
  - `maxAge: 604800000` (7-day rolling window)
- **Hardened Cookie Invalidation**: Both `clearAuthCookies` and stale session rejection pass `{ path: '/', httpOnly: true, secure: true, sameSite: 'lax' }` to ensure modern browsers accept `Set-Cookie` deletion headers under the `__Host-` specification.

## 13. CSRF Protection

- **Double-Submit Pattern**: Cookie `nexora_csrf` (`HttpOnly: false`, `SameSite: Lax`, `Path: /`, `Secure: true` in production) paired with request header `x-csrf-token` / `X-CSRF-Token`.
- **Timing-Safe Verification**: Cryptographic timing-safe comparison (`crypto.timingSafeEqual`) prevents timing attack vulnerabilities.
- **Safe Method Bypass**: Safe read-only methods (`GET`, `HEAD`, `OPTIONS`) bypass CSRF validation.
- **Dedicated Webhook Exemption**: Razorpay asynchronous webhook endpoint (`/api/webhooks/razorpay`) is exempt from CSRF and secured exclusively via HMAC-SHA256 signatures.

## 14. Strict CORS Architecture

CORS policy (`src/middleware/cors.js`) enforces strict origin validation:
- **Allowed Origins**: Configured via `CORS_ORIGIN` (e.g., `https://app.nexora.com`).
- **No Wildcards**: Wildcard `*` is explicitly blocked in production configuration.
- **Allowed Headers**: Includes `Content-Type`, `Authorization`, `X-Request-Id`, `X-Guest-Token`, `X-Guest-Order-Token`, `Idempotency-Key`, and canonical `X-CSRF-Token`.
- **Preflight Caching**: `maxAge: 86400` (24 hours).

## 15. Guest Checkout Security

- **Single-Use Raw Token**: 256-bit CSPRNG token returned exactly once in the response payload upon guest session creation.
- **Hashed at Rest**: SHA-256 hash stored in PostgreSQL; raw token is never persisted in database.
- **Frontend Invariant**: Token stored strictly in React memory (`useState`); never saved to `localStorage`, `sessionStorage`, cookies, or URLs.
- **Transport Security**: Transmitted via `X-Guest-Token` header.
- **Anti-IDOR Defense**: All guest order lookup endpoints return sanitized 404 for mismatched tokens.

- **Test Mode Enforced**: Deployment configuration utilizes Razorpay Test Mode keys (`rzp_test_...`).
- **Backend-Only Secrets**: `RAZORPAY_KEY_SECRET` and `RAZORPAY_WEBHOOK_SECRET` reside exclusively on backend environment and are never transmitted to frontend or client bundle.

## 17. Razorpay Webhook Readiness

- **Endpoint**: `POST /api/webhooks/razorpay`
- **Raw Body Preservation**: Body parser captures raw buffer (`req.rawBody`) for exact byte-level HMAC signature verification.
- **HMAC-SHA256 Verification**: Signatures verified against `RAZORPAY_WEBHOOK_SECRET` using `crypto.timingSafeEqual`.
- **PaymentEvent Lifecycle**: Webhook events logged with authoritative state tracking across the full lifecycle: `RECEIVED` → `PROCESSING` → `PROCESSED`, `FAILED`, or `REQUIRES_REFUND` (with `IGNORED_DUPLICATE` for idempotent replays).
- **Idempotency**: Duplicate event IDs are recognized and return 200 without duplicate state mutations.
- **Authoritative Settlement**: Webhook `payment.captured` event settles order to `PAID` and converts reserved stock to permanent sale.

## 18. Inventory Deployment Concurrency

- **PostgreSQL-Authoritative**: Row-level locking (`SELECT ... FOR UPDATE`) with deterministic ordering (`ORDER BY id ASC`) prevents deadlocks during multi-item reservations.
- **Check Constraints**: `chk_products_reserved_lte_stock` enforces `reserved_stock <= stock` at the storage layer.
- **No Caching / No Eventual Consistency**: Stock checks always read committed PostgreSQL state.
- **Refund != Restock**: Admin refund does not automatically increment stock; restocking requires explicit, audited manual restocking actions via canonical route: `POST /api/admin/orders/:id/restock`.

## 29. Rollback & Recovery Procedure

### Application Service Rollback
1. Trigger revision rollback to previous immutable container image / deployment artifact.
2. Verify previous container passes `/api/health/ready`.
3. Re-route load balancer traffic to the rolled-back revision.

### Database Migration Considerations
1. **Prefer Forward-Fixes**: Because schema rollback on live databases can cause data loss or service disruption, forward-fixing via an additive migration is strongly preferred over destructive rollbacks.
2. **Backward-Compatible Migrations**: Phase 07 migrations do not drop columns or tables containing live business data.
3. **Emergency Point-in-Time Recovery**: In the event of fatal schema corruption, initiate managed PostgreSQL PITR restore to the pre-deployment timestamp snapshot.

### External Payment State Invariant
- **Never Roll Back External Gateway State**: If a deployment failure occurs during payment processing, external Razorpay payments must never be manually deleted. Run backend reconciliation jobs against `payment.captured` webhooks to synchronize payment states deterministically.

## 32. Changes Rejected

1. **Rejected Redesigning Authentication to JWT**: Server-side sessions in PostgreSQL are authoritative per frozen architecture.
2. **Rejected Adding Redis for Caching / Rate Limiting**: PostgreSQL and in-memory rate limiting satisfy all p95 performance targets (< 35 ms) without introducing stateful SaaS dependencies.
3. **Rejected Multiple CORS Header Casing Variants**: HTTP header names are case-insensitive; added canonical `X-CSRF-Token` only.
4. **Rejected Blindly Upgrading Sequelize v6**: Upgrade to Sequelize v7 would violate frozen architecture without resolving accepted cast-type issues already mitigated by Zod.
5. **Rejected Automatic Seeding in Production**: Seeding is strictly an explicit administrative action via `npm run db:seed`.

## 33. Remaining Limitations

1. **Multi-Instance Rate Limiting**: In-memory rate limiting tracks requests per Node.js process. In a horizontally scaled cluster (multiple backend replicas), rate limits apply per-replica unless sticky sessions are configured at the load balancer.
2. **Managed Cloud Infrastructure**: Real cloud deployment requires provisioning managed PostgreSQL, SSL certificates, domain DNS, and cloud secrets via cloud console or Terraform.
3. **External Razorpay Webhook Delivery**: Webhook signature verification and idempotency are fully validated locally with real HMAC signatures; public reachability requires deploying backend to a public HTTPS domain.
