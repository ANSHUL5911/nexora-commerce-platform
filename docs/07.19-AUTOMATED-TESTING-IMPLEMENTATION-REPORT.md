## 3. Frozen Architecture Compliance

All frozen architectural baselines were rigorously honored:
- **No Architectural Changes**: No microservices, GraphQL, or JWT authentication were introduced.
- **Authoritative Database**: PostgreSQL (`nexora_test`) remains the sole transactional authority with row locks (`SELECT ... FOR UPDATE`), partial unique indexes, and foreign keys.
- **Session Authority**: Server-side sessions remain authoritative with `__Host-nexora_sid` cookies (`HttpOnly`, `SameSite=Lax`, `Path=/`, no Domain).
- **Payment Authority**: Razorpay frontend returns remain non-authoritative; backend verification and `payment.captured` webhooks remain authoritative.
- **Guest Token Architecture**: Tokens remain ephemeral in React memory only; zero storage in `localStorage`, `sessionStorage`, or URL query strings.
- **Inventory Semantics**: Strict separation between reservations (`ACTIVE`), conversions (`CONVERTED`), and explicit administrative restock (`StockRestockLog`).
- **Critical Invariant Maintained**: `REFUND != RESTOCK`. A refund never increases stock.

## 11. Concurrency Tests

Tested against real PostgreSQL using `Promise.all` and `Promise.allSettled`:
1. **Inventory Reservation Race** (`inventory.concurrency.test.js`):
   - 10 concurrent requests for 1 unit of a product with `stock=1`. Exactly 1 succeeds (200), 9 receive 409 `INSUFFICIENT_STOCK`. Final DB state: `stock=1, reserved=1, available=0`.
2. **Multi-Quantity Reservation Race**:
   - Competing 6-unit and 4-unit requests on `stock=10` both succeed.
   - Competing 6-unit and 6-unit requests on `stock=10` allow exactly one success and one conflict.
3. **Lost Update Prevention**:
   - 10 concurrent requests of quantity 1 against `stock=10` all succeed without lost updates (`reserved=10, stock=10`).
4. **Expiry vs Conversion Race**:
   - Concurrent execution of reservation conversion and background expiration processing guarantees exactly one terminal transition (`CONVERTED` or `EXPIRED`) with zero double decrements.

## 16. Transaction Checkpoint Rollback Tests

Implemented in `tests/database/rollback.test.js`:
Using surgical failure injection at precise transactional checkpoints, complete rollback was verified with zero orphaned rows:
1. **Checkpoint A (After Order INSERT, before OrderItems)**: Simulated error on `orderRepository.createOrderItems`. Result: `orders = 0, order_items = 0, reservations = 0, cart = 1 item, stock = 10, reserved = 0`.

3. **Checkpoint C (Before cart clear / commit)**: Simulated error on `CartItem.destroy`. Result: complete rollback of order and reservation; cart remains intact.
4. **Checkpoint D (During settlement conversion)**: Simulated error on `inventoryService.convertReservation`. Result: `Order` remains `PENDING_PAYMENT`, `PaymentAttempt` remains `INITIATED`, `Reservation` remains `ACTIVE`.
5. **Checkpoint E (During administrative restock)**: Simulated error on `StockRestockLog.create`. Result: stock quantity does NOT increment; 0 restock logs created.

## 17. Security Regression Tests

Implemented in `tests/security/security.regression.test.js`:
- **SQL Injection**: Injection strings in search queries (`' OR '1'='1`, `'; DROP TABLE products; --`, `1' UNION SELECT...`) execute safely through parameterized queries without errors or schema alteration.
- **XSS Input Safety**: HTML and script strings (`<script>alert("XSS")</script>`) in text fields (`full_name`) are accepted and stored as inert text, returning safely in JSON DTOs without execution.
- **Path Traversal**: Traversal strings (`..%2F..%2F..%2Fetc%2Fpasswd`, invalid UUIDs) in route parameters return 400 or 404 safely.
- **Quantity Validation**: Negative, zero, float, and non-numeric quantities in cart mutations are rejected with 400 `VALIDATION_ERROR`.
- **Prototype Pollution**: Payloads containing `__proto__` and `constructor` do not pollute `Object.prototype`.
- **DTO Sanitization**: Responses never expose `password_hash`, session SIDs, raw guest tokens, or database credentials.
