## 1. Executive Summary & Scope

Phase 07.2 established the authoritative PostgreSQL relational database foundation for the Nexora Commerce Platform. The implementation executed strictly in accordance with frozen specifications `05-BACKEND-SCHEMA-v1.0.md`, `06-IMPLEMENTATION-PLAN-v1.0.md`, and `07.0-IMPLEMENTATION-BASELINE.md`.

### Implemented Capabilities:
- PostgreSQL development (`nexora_dev`) and dedicated test (`nexora_test`) database configuration.
- Single authoritative programmatic and CLI migration runner using Umzug and Sequelize storage (`SequelizeMeta`).
- 11 deterministic, reversible Sequelize migrations provisioning the exact 14 domain business entities.
- Full constraint and index enforcement:
  - Non-negative inventory counters (`stock_quantity >= 0`, `reserved_quantity >= 0`, `reserved_quantity <= stock_quantity`).
  - Strict integer Paise currency representation (`BIGINT`) with non-negative constraints.
  - One active cart per user constraint (`uq_carts_user`) and composite cart-item uniqueness (`uq_cart_items_cart_product`).
  - Partial unique indexes (`idx_payment_attempts_rzp_order`, `idx_payment_attempts_rzp_payment`, and `uq_one_success_payment_per_order`).
  - Scoped API idempotency mutual exclusion `(idempotency_key, request_path)`.
  - Webhook deduplication `(event_id)` and status lifecycle checks.
  - Single shipping profile per customer in MVP (`uq_addresses_user`) and 6-digit Indian PIN verification.
- Deterministic, Razorpay-neutral seed fixtures for development and test environments.
- Comprehensive automated verification test suites covering full migration lifecycle (UP $\rightarrow$ VERIFY $\rightarrow$ SEED $\rightarrow$ VERIFY $\rightarrow$ DOWN $\rightarrow$ RE-APPLY) and exhaustive PostgreSQL-level constraint assertions.

## 3. Authoritative PostgreSQL Database Architecture

### 3.1 Exactly 14 Domain Business Entities
The database schema consists of exactly 14 domain business entities:

```
┌────────────────────────────────────────────────────────────────────────┐
│                        NEXORA RELATIONAL SCHEMA                        │
├─────────────────────────┬────────────────────────┬─────────────────────┤
│ 1. Identity & Sessions  │ 2. Catalog & Inventory │ 3. Cart & Orders    │
│  - users                │  - products            │  - carts            │
│  - sessions             │  - inventory_          │  - cart_items       │
│  - addresses            │    reservations        │  - orders           │
│                         │  - stock_restock_logs  │  - order_items      │
├─────────────────────────┴────────────────────────┴─────────────────────┤
│ 4. Payments, Idempotency & Audit Logs                                  │
│  - payment_attempts                                                    │
│  - payment_events                                                      │
│  - idempotency_records                                                 │
│  - audit_logs                                                          │
└────────────────────────────────────────────────────────────────────────┘
```

### 3.2 Inventory Concurrency Invariants
- `products.stock_quantity` ($\ge 0$) and `products.reserved_quantity` ($\ge 0$).
- Enforced constraint: `CHECK (reserved_quantity <= stock_quantity)`.
- Dynamic calculated available stock:
  $$\text{available\_quantity} = \text{stock\_quantity} - \text{reserved\_quantity}$$
- `available_quantity` is **never** persisted as an independent mutable column.
- Inventory reservation records (`inventory_reservations`) bind uniquely at the `(order_id, product_id)` aggregate level.

### 3.3 Monetary Invariants
- All monetary amounts across all tables (`products.price_paise`, `orders.total_cost_paise`, `orders.shipping_fee_paise`, `order_items.unit_price_paise`, `payment_attempts.amount_paise`) are stored as **Integer INR Paise** (`BIGINT`).
- Floating-point data types (`FLOAT`, `DOUBLE PRECISION`, `REAL`) are strictly prohibited.
- All monetary columns are guarded by `CHECK (... >= 0)` constraints.

### 3.4 Multi-Attempt Payment & Partial Unique Indexes
- $1:N$ relationship between `orders` and `payment_attempts`.
- Payment retries attach a new `payment_attempts` row with incremented `attempt_number` without duplicating orders or creating duplicate inventory holds.
- Partial unique indexes ensure gateway identifier consistency:
  - `CREATE UNIQUE INDEX idx_payment_attempts_rzp_order ON payment_attempts(razorpay_order_id) WHERE razorpay_order_id IS NOT NULL;`
  - `CREATE UNIQUE INDEX idx_payment_attempts_rzp_payment ON payment_attempts(razorpay_payment_id) WHERE razorpay_payment_id IS NOT NULL;`
  - `CREATE UNIQUE INDEX uq_one_success_payment_per_order ON payment_attempts(order_id) WHERE status = 'SUCCESS';`

### 3.5 Webhook Idempotency & Scoped Mutual Exclusion
- `payment_events.event_id` is uniquely constrained (`uq_payment_events_event_id`).
- Webhook lifecycle status starts at `RECEIVED` and transitions across `('RECEIVED', 'PROCESSING', 'PROCESSED', 'IGNORED_DUPLICATE', 'REQUIRES_REFUND', 'FAILED')`.
- `idempotency_records` enforces mutual exclusion scoped strictly to `(idempotency_key, request_path)` via `uq_idempotency_scope`.

### 3.6 Security & Data Classification Boundary
- **Zero Cardholder Storage:** Zero tables or columns for raw card numbers, CVVs, expiration dates, PINs, or MPINs.
- **Zero Persistent Signatures:** Razorpay HMAC signatures are verified transiently in memory; zero database columns exist for signatures.
- **Guest Order Security:** `orders.guest_token_hash` stores 64-character SHA-256 hash of 256-bit CSPRNG token. Raw guest tokens are never persisted.
- **Server-Side Sessions:** `sessions` table utilizes 256-bit random opaque identifiers (`sid` PRIMARY KEY). JWT tokens are completely excluded.
